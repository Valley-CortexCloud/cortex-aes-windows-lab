# Cortex AES — POV test plan (Windows lab)

A test matrix for evaluating Koi / Cortex AES. Each case has an **objective**, the
**steps**, and a **pass criterion** you can put in a POV scorecard for ADP.

Your ground truth is `provisioning/expected-inventory.json` (generated by
`05-inventory.ps1`). Most cases boil down to: *did the AES console match reality?*

Legend: 🟢 core / must-pass · 🟡 differentiator · 🔵 nice-to-have

---

## 1. 🟢 Discovery coverage
**Objective:** Does AES find everything we planted?
**Steps:** Run the light-up payload → deploy Koi (method 1) → let it report →
open the endpoint in the AES console.
**Pass:** Every item in `expected-inventory.json` appears — VS Code extensions,
browser extensions (Chrome + Edge), MCP servers (filesystem/memory/github/sequential-thinking),
and AI tools (Cursor, Windsurf, Claude Desktop, Ollama). Note any misses.

## 2. 🟢 Version accuracy
**Objective:** Are reported versions correct (for CVE/compliance tracking)?
**Steps:** Compare the versions in the console against `--show-versions` output and
browser manifest versions in the inventory.
**Pass:** Versions match. Then upgrade one extension and confirm AES reflects the new
version on the next run.

## 3. 🟡 MCP server detection
**Objective:** This is the headline agentic capability — validate it hard.
**Steps:** Confirm all three MCP config locations are detected (Claude Desktop,
Cursor, VS Code workspace). Add a 4th MCP server by hand to one config, re-run.
**Pass:** New server shows up; AES distinguishes servers per host app and shows the
command/args or a risk note.

## 4. 🟡 Risk scoring / AI researcher
**Objective:** Exercise the LLM-driven risk engine.
**Steps:** Look at the AES risk score for a broad-permission item (e.g. the password-
manager browser extension, or GitLens). Install one deliberately obscure/low-reputation
extension and compare its score + the reputation/exploitability/intent/privilege signals.
**Pass:** Scores are differentiated and the rationale is legible — not every item is "medium".

## 5. 🟢 Multi-user profile coverage
**Objective:** Prove discovery spans all local users, not just the installer.
**Steps:** Create a 2nd local user, log in as them over RDP, install 1–2 VS Code
extensions + a browser extension, log out. Re-run Koi.
**Pass:** The 2nd user's items appear, attributed to that user context.

## 6. 🟢 Remediation — removal
**Objective:** Prohibited item is actually removed from disk, not just flagged.
**Steps:** In the console, mark one extension prohibited / set a remediation policy.
Let Koi run.
**Pass:** The extension's files/directories are gone from the user profile; the
console shows it remediated. Verify on disk.

## 7. 🟡 Remediation — reinstall block
**Objective:** Does enforcement stop the user putting it back?
**Steps:** As the user, try to reinstall the remediated extension.
**Pass:** Install is blocked by the deployed policy (where the app supports local
blocklisting), or it's removed again on the next run. Record which apps support hard
block vs re-remediate.

## 8. 🟢 Deployment-method comparison
**Objective:** Confirm all three run styles report identically and document the UX.
**Steps:** Run method 1 (manual), method 1b (scheduled task), method 2 (service).
Between each, note setup effort, time-to-first-report, and where logs live.
**Pass:** Same discovery result regardless of method. Fill the method table in
`koi/README.md` with your observed times.

## 9. 🟡 Update behaviour (managed vs manual)
**Objective:** Validate the auto-update wrapper and the manual path.
**Steps:** On the service install, confirm it picks the chosen update mode. For manual
mode, drop a newer `mdm.ps1` in `C:\ProgramData\Koi\` and confirm it's used next run.
**Pass:** Managed mode self-updates with no action; manual mode uses the dropped file.

## 10. 🔵 Grouping via hosts/PAC signature (OFF by default)
**Objective:** Understand the device-grouping mechanism — only if ADP wants network-level.
**Steps:** Enable the network-config option in the deployment, re-run, inspect
`C:\Windows\System32\drivers\etc\hosts` for the tagged `# KOI_HOST` entries and the
PAC/proxy registry settings.
**Pass:** You can explain what it writes, that the domain is Koi-owned/unused, and how
to turn it off. **Leave disabled unless ADP explicitly asks** — it modifies host/proxy config.

## 11. 🟢 Uninstall / rollback
**Objective:** Clean removal — important for POV exit criteria.
**Steps:** `uninstall.ps1` (service only), then on a fresh deploy `uninstall.ps1 -Rollback`.
**Pass:** Service gone, `C:\ProgramData\Koi` handled, and with `-Rollback` any PAC/hosts/
policy changes are reverted.

## 12. 🟡 Performance impact
**Objective:** Back the "minimal impact" claim with numbers for ADP.
**Steps:** Capture baseline CPU/RAM, then sample during a Koi run
(`Get-Counter '\Process(*koi*)\% Processor Time'`, or Task Manager). Note WinPython
first-run download time vs steady-state run time.
**Pass:** Steady-state runs are short and low-footprint; you have real figures to quote.

## 13. 🟡 Runtime Agent Activity (AIDR)
**Objective:** Prove Koi captures live AI *coding agent* sessions — the headline
runtime capability. **Note: Claude Desktop does NOT count** (not a coding agent);
you need Claude Code / Cursor / Codex / Copilot CLI. See `aidr-runtime-activity.md`.
**Steps:** Install Claude Code CLI (`06-install-coding-agents.ps1`), authenticate,
run a task that uses a tool (`claude -p "create a file..." --dangerously-skip-permissions`).
**Pass:** A session appears in Runtime Agent Activity with the tool action in its
timeline, shown as governed by the deployed enforcement policy. Bonus: set a block
policy and confirm the action is stopped inline.

## 14. 🔵 Reporting / endpoint view
**Objective:** Validate the console's endpoint fields for ops handoff.
**Steps:** In **Covered endpoints**, confirm Hostname, Last seen, Registered at,
Script version, Serial — cross-check Serial/Hostname against the inventory.
**Pass:** Fields are populated and accurate; "Deployed" badge + coverage bar reflect reality.
